下载预读另覆盖乱序响应、跨文件共享两个请求槽位、提前关闭后取消全部读任务、服务端限速后不继续派发、分段长度错误、断点恢复后的完整文件 SHA-256、真实 Telethon 迭代器配合模拟 RPC 的偏移范围，以及密集和低频数据到达下的平均速度计算。核心和预读两种 32 MiB 以上流的 Python 跟踪内存峰值均断言低于 8 MiB，不包含系统缓存或程序基线。

`pipeline-benchmark.json` 是固定每分段 80 ms 延迟的离线模拟：单分段 1.1175 秒，双分段 0.5708 秒，结果哈希一致。它只证明能重叠请求等待，**不代表 Telegram 或用户代理线路能提速 1.958 倍**。实际网络速度需要用户升级后自行观察。

核心测试使用假 Telegram 传输层，不连接真实账号；另用实际安装的 Telethon 1.45.0 类型验证媒体消息/迭代器调用兼容性。覆盖文件逐字节和 SHA-256 对比、短写处理、错误长度、损坏片段、未提交尾部、短暂断网、有限重试、服务器等待、权限拒绝、视频串行和总并发上限、磁盘写满、SQLite 完成提交失败、暂停继续、扫描取消和退出。

内存测试在不预加载完整源文件的情况下生成并保存 32 MiB 以上的流，断言 Python 跟踪内存峰值低于 8 MiB。该数值不包含操作系统缓存、Python/GUI 基线、Telethon 已连接后的运行开销，不代表多 GB 真实频道压力测试已经完成。

Windows DPAPI 使用仅供测试的虚构字符串做加密/解密回环，并检查配置中不存在这些字符串的明文。正常登录、两步验证和 API 调用在测试中使用模拟对象；不会发送验证码或处理真实手机号。

尚待用户本机完成的在线验收：自己的 API ID/Hash 与账号登录、现有代理、目标频道真实 API 返回范围、小图片/视频打开播放、大视频实际内存与磁盘表现、真实 Telegram FloodWait 和访问拒绝。没有真实账号在线证据前，不能称为支持整个受限频道下载。

建议首次验收：只扫描 10–20 条视频，选空目录，下载两个文件并正常打开，下载较大文件中途暂停、退出、恢复登录再继续；确认完成数、原文件大小和播放情况后再扩展日期/历史范围。测试过程中无需发送登录秘密。
